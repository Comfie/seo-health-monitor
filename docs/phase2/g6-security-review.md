# G6 focused security review

15 October 2026, local source on `phase2-multiuser`. This is an application/code and negative-test review, not an independent penetration test or a claim of complete security. Hosted G6 evidence must follow an approved deployment.

Review basis: OWASP guidance on [authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), [authentication and sensitive-operation reauthentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), [SSRF prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) and [safe logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html). Default-deny server checks, ownership at the repository boundary, and negative tests are the primary controls.

## Streamed protected-page not-found behaviour

Reproduced in the local browser: an ordinary customer requesting `/beta/admin` receives HTTP **200** with the generic not-found UI and no customer/admin records. The installed Next.js 16.4 guide, `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/not-found.md`, explicitly documents 200 after streaming starts, versus 404 before streaming; `notFound()` also injects noindex. Cache Components/Suspense can commit the shell before request-time DB authorisation completes. Sensitive queries remain after authorization; all admin APIs deny with real 404 (401 for no session).

Kept this documented framework behaviour. Moving DB authorization into the optimistic proxy or removing streaming application-wide would broaden the change and risks weakening the established boundary. A shell status/title is not an authorization result. Monitor the API statuses and presence of protected content; never infer access from HTML status 200 alone. A future routing-level 404 improvement is optional, provided it preserves DB checks and no-store behaviour.

## Dependency audit (live npm advisory query, 15 October 2026)

No dependency or lockfile upgrade was made. `npm audit --json` still reports **13 findings: 9 high, 4 moderate; 0 critical**, matching the recorded baseline. Nine high paths concern development tooling (`braces` → micromatch/fast-glob → shadcn/ts-morph/Next ESLint); four moderate paths concern drizzle-kit's old esbuild/esm-loader chain. npm's suggested broad fixes include incompatible major downgrades; do not run `npm audit fix --force`.

Primary advisories: [braces stack exhaustion](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm) and [esbuild development-server request exposure](https://github.com/advisories/GHSA-67mh-4wv8-2f99). The former matters when a developer tool handles malicious glob patterns; the latter requires use of the vulnerable development server. Neither development server nor public glob-processing endpoint is introduced here. Web standalone tracing and worker runtime dependencies must be checked on the final build. The worker's production install may retain unused drizzle-kit/esbuild via existing optional dependency resolution; do not treat a development label as proof a package is absent. No vulnerable developer server should be reachable in production.

Recorded residual risk requires operator review/acceptance before external invitations, or a separately tested dependency fix. The review does not relabel an advisory as fixed. Final Linux image scanning and hosted negative tests remain deployment gates. No new third-party dependency was added for G6.
